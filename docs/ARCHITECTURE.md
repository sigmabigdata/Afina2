# Архитектура Afina2

## Принципы

1. **API-first**: весь функционал доступен через REST `/api/v1`; SPA не зависит от серверных шаблонов.
2. **Сертифицированное ядро**: ОС, СУБД, JDK, веб-сервер и СКЗИ — сертифицированные компоненты; UI-библиотеки не выполняют криптографических и защитных функций.
3. **Криптография только в сертифицированном провайдере**: подпись в браузере — плагин КриптоПро, проверка на сервере — JCSP. BouncyCastle — только разбор ASN.1/CMS-структур.
4. **Один домен, cookie-сессии**: SPA и API на одном origin за Angie; CSRF-токен, SameSite, CSP.
5. **Аудит всего**: каждое действие пользователя/администратора пишется в `audit_events`.

## Компоненты

```
Browser (React 18 + Ant Design 5)
  ├─ КриптоПро CAdES plugin (подпись на рабочем месте, ключ не покидает носитель)
  └─ fetch /api/v1/* (cookie-сессия, CSRF-заголовок)

Angie 1.12 (TLS, CSP, раздача SPA, прокси /api)
  └─ Spring Boot 3.2 / Axiom JDK 17
       ├─ auth: magic-link, вход по сертификату, онбординг
       ├─ documents / folders / signatures (CAdES-BES, ГОСТ 34.10-2012)
       ├─ templates: генерация PDF по HTML-шаблону
       ├─ Госключ: заявки, пакеты до 15 файлов, статусы ЕПГУ
       ├─ CRL / truststore / проверка подписи (JCSP)
       ├─ визуализация штампов и справка о подписании (PDF)
       └─ admin: клиенты, аудит, настройки, мониторинг, бэкапы, ключи, МЧД
  └─ PostgreSQL 15 (разделение привилегий: migrator / app / auditor)
```

## Ключевые сценарии

### Подписание документа

1. SPA получает содержимое (`GET /api/v1/documents/{id}/content`).
2. Плагин КриптоПро формирует отсоединённую подпись CAdES-BES по ГОСТ 34.10-2012.
3. SPA отправляет base64 на `POST /api/v1/documents/{id}/sign`.
4. Сервер: скачивает CRL по CDP, проверяет подпись и цепочку (JCSP), пишет аудит,
   сохраняет подпись, генерирует PDF-визуализацию, уведомляет клиента письмом.
5. Повторное подписание тем же пользователем отклоняется (409).

### Госключ

1. `POST /api/v1/documents/{id}/gosklyuch` (один документ) или
   `POST /api/v1/documents/folders/{folderId}/gosklyuch` (пакет до 15 файлов).
2. Сервер собирает XML + ZIP, подписывает пакет УКЭП организации и отправляет в ЕПГУ.
3. Планировщик обновляет статусы, сохраняет полученную подпись и применяет её
   после проверки; администратор может обновить/применить вручную.

### Онбординг клиента

1. Первый вход по magic-link → профиль не заполнен → 403 `profile_required`.
2. `POST /api/v1/auth/profile` — ФИО и телефон.
3. `GET /api/v1/auth/consent` — сервер генерирует PDF согласия по шаблону
   назначения `CONSENT` и кладёт в раздел «Согласия».
4. Клиент подписывает согласие УКЭП → ограничения на загрузку снимаются.

### Админка

REST-таблицы: клиенты, документы, заявки, аудит, CRL, настройки, мониторинг,
бэкапы, ключи, МЧД. Опасные операции (восстановление, очистка) — только
администратор, с подтверждением и записью в аудит.

## Аутентификация и сессии

- клиент: magic-link на e-mail (одноразовый токен, TTL 10 ч, многоразовый в пределах TTL);
- сотрудник/администратор: сертификат УКЭП (challenge → подпись → сессия),
  CN и СНИЛС сверяются с `admins.env` или карточкой сотрудника;
- сессия: cookie `AFINA2SESSION`, `HttpOnly`, `Secure` (в prod), `SameSite=Lax`;
- CSRF: double-submit cookie `XSRF-TOKEN` → заголовок `X-XSRF-TOKEN`;
- rate limit: 5 попыток входа / 15 мин на IP; 10 челленджей / 15 мин;
- IP-whitelist на `/api/v1/admin/**` (CIDR поддерживается);
- неавторизованный запрос к API — JSON 401 без редиректов.

## Шифрование данных

| Что | Как |
|---|---|
| Файлы документов | AES-256-GCM, ключи `secrets/keys/file.key.vN`, версия хранится в документе |
| Персональные данные (e-mail, телефон, СНИЛС, ИНН, паспорт) | AES-256-GCM через JPA-конвертеры + хэши для поиска |
| Бэкапы | архив шифруется паролем (AES-256), пароль не хранится в приложении |
| Ключи | генерируются автоматически при первом старте, права 0600; выгружаются только ZIP с паролем |

## Наблюдаемость

- `/api/v1/health` — публичный health; `/actuator/health` — для оркестратора;
- журнал аудита с фильтрами и выгрузкой CSV;
- мониторинг компонентов (БД, диск, CRL, SMTP, хранилище) с историей;
- структурные логи с маскированием PII (e-mail, ФИО, токены).
